# Profile 重构与冗余清理后的性能复测

测试日期：2026-10-20（Asia/Shanghai）。范围是本轮开始的 Profile 重构工作区，以及本轮冗余清理后的工作区。
测试真实 `MyLLM.generate()` 和官方 SDK，HTTPX 内存响应不建立 socket，不等待网络或模型推理。

本文两份源码都已删除未知字段保留，只衡量后续清理。删除前提交与当前修复的对照、
回退原因和最新结果见[性能回退定位](performance-regression-2026-10-20.md)。本文数字保留为当时的测量记录。

## 本轮结果

清理前后各完成 **60 场景、600 个暖样本**，每个场景还包含独立实例预检、冷调用和额外 2 次预热。
逐场景 P50 变化的中位数为 **-9.82%**，范围 **-48.19% 至 +0.59%**；
57 个下降、3 个上升。下面是各协议复杂原生负载的对照，单位 ms。

| 协议 | 聚合 P50：清理前 → 后 | 变化 | 完整流式 P50：清理前 → 后 | 变化 |
| --- | ---: | ---: | ---: | ---: |
| Chat | 26.92 → 26.86 | -0.22% | 26.61 → 26.77 | +0.58% |
| Responses | 66.28 → 65.67 | -0.92% | 66.35 → 65.58 | -1.16% |
| Anthropic | 50.85 → 47.09 | -7.38% | 51.29 → 47.02 | -8.32% |
| Gemini | 107.39 → 67.54 | -37.11% | 106.69 → 68.09 | -36.18% |
| Ollama | 21.59 → 19.64 | -9.03% | 21.75 → 19.50 | -10.35% |

Chat / Responses 的本轮变化接近持平；Anthropic / Ollama 有较小下降，Gemini 的下降较明显。
这是一轮先测 before、再测 after 的同机观测，没有做随机交替或统计显著性检验；不把单次百分比当作稳定收益承诺。
每个场景仅 10 个暖样本，nearest-rank P95 等于该组最大值。默认 GC、调度和 SDK 内部行为仍会影响尾部耗时。

## 复制与 SDK 热点的独立诊断

另用两个独立 Python 子进程分别加载清理前源码快照与当前源码，每个原生场景预检、冷调用和预热后，
只对一次完整暖调用启用 cProfile，合计 10 对场景。I/O 字节、事件和分块逐项相同，GC 保持默认设置。
下表是 deepcopy 总调用数（包含递归），不是整份请求的副本数量；两种返回模式的计数相同。

| 协议 | 清理前 | 清理后 | 减少 |
| --- | ---: | ---: | ---: |
| Chat | 28,991 | 27,643 | 4.65% |
| Responses | 38,527 | 37,717 | 2.10% |
| Anthropic | 77,995 | 51,968 | 33.37% |
| Gemini | 251,807 | 102,035 | 59.48% |
| Ollama | 63,606 | 50,722 | 20.26% |

这些计数直接证明重复遍历减少；延迟收益仍以上面的无 profiler 基准为准。
诊断中仍出现的热点包括 OpenAI / Anthropic SDK 的 `_async_transform_recursive`，以及 Gemini SDK 的
`convert_to_dict`、`encode_unserializable_types`。它们处理原生参数、SDK 模型和 JSON 序列化，
不属于 MyLLM 编排中的不同执行分支。

cProfile 会显著放大耗时；inclusive/cumulative 时间相互重叠，不能相加为互斥占比或当作真实延迟。

## 代码与执行路径结论

本轮删除字段提取后的提前深拷贝、原生结构的重复 SDK 投影和明确协议下的无效推测准备；
保留 Encoder / Decoder 公开结果隔离、Transport 独立请求数据、StreamState 状态捕获和最终结果副本。
五协议共用请求和返回编排，具体字段、原生事件与 SDK 生命周期差异留在各协议实现中；
共享状态机不再维护 Responses 专属字段清单，改用原生 Encoder 明确投影的 metadata(values, path)。
无状态注册新增 MRO 数据槽检查，依赖边界测试覆盖各协议 utils；独立第六协议证明新元数据可以接入而不修改共享层。
完整证据与需要保留的校验见[执行路径和抽象契约审计](request-path-audit-2026-10-20.md)。
在该次清理结束时，Gemini config.tools 仍有根配置与工具入口的重复投影；
后续已在[性能回退修复](performance-regression-2026-10-20.md)中解决，该处不再代表当前实现。

相同编排不代表耗时相同。SDK 请求序列化、输入/响应结构、事件数量以及 SDK 类型验证仍有不同成本。
例如原生 Responses 有 244 个上游事件，而 Chat 为 116；Gemini 的配置、工具及输入结构约 984 KB，仍需完整 SDK 类型验证。
本轮移除重复工作，不省略必要的源协议与目标协议校验，也不以未知字段恢复机制简化翻译。
