# 新协议缓存通用性与缓存策略审计

测试日期：2026-10-20（Asia/Shanghai）。基线为 Parameter / Config 重构完成后的源码；本文只评估随后对缓存键、容量和批量计划查询的修改，不重复计算此前构造缓存的收益。

## 结论

缓存依赖类型声明、参数路径和抽象组件契约，不依赖五种内置协议名称。独立新协议能够复用同一条缓存执行路径。发现的边界问题已修复，批量过滤有明确微基准收益；完整请求仍接近持平。

| 检查项 | 结果 |
| --- | --- |
| 新协议的 Schema 与验证器 | 使用自己的 TypedDict / Pydantic 类型和受支持的容器、Union 等注解，自动进入共享缓存；不需要修改协议白名单。 |
| 同名类型隔离 | 按类型对象及有序泛型结构区分，不按类型名字符串索引；两个同名 NativeMessage 不共享错误规则。 |
| Annotated 的不可哈希元数据 | 原先过滤计划支持，但验证器和路径缓存直接 hash(schema) 会失败；现在统一使用 _SchemaKey，完成实际新协议生成验证。 |
| Union 的声明顺序 | 过滤计划与验证器缓存均保留声明顺序，避免 Python Union 的顺序无关相等比较合并不同规则。 |
| 动态协议类型的容量 | 五类进程级 Schema 缓存各设 512 个 LRU 入口；超过容量后可以重新编译，输出不变。 |
| 请求隔离 | 缓存不保存消息、工具参数、响应或先前 Union 分支；批量处理仍逐条过滤、验证和复制应拥有的数据。 |

## 其他缓存是否依赖内置协议

| 缓存 | 键或所有者 | 新协议的行为 |
| --- | --- | --- |
| Profile 声明分析 | dataclass 类型，LRU 128 | 自定义 ProtocolDefaults / ProviderProfile / ModelProfile 子类按自身类型分析；不缓存实例配置值。 |
| 参数路径解析 | 路径字符串，LRU 512 | 缓存不可变路径分段；每次沿当前请求或响应读取，不缓存此前的字段值或缺失结果。 |
| SDK 客户端 | MyLLM 实例和 Transport.client_key | 默认新协议复用该实例的客户端；SDK 若把可变调用设置绑定在客户端上，协议所属 Transport 需定义对应的复用键。 |
| SDK 模型字段视图 | 当前 _ModelView | 当前转换内缓存字段及子视图，下次转换读取更新值。 |
| 流内容物化 | 当前 BlockState / StreamState | 通过公共块操作失效、重建，不按来源协议名缓存最终内容；独立协议已有流、元数据与关闭测试。 |

客户端缓存没有改为简单的 LRU / TTL：连接仍可能被并发请求借用，直接淘汰并关闭会破坏资源生命周期。客户端由 MyLLM.aclose 统一释放；本次仅为类型规则缓存增加容量限制。

这不是支持任意 Python 对象或自动识别全新协议。新协议仍需实现 Encoder / Decoder / Transport，并声明过滤器支持的类型。运行中原地修改同一个类型对象的字段没有自动失效保证，应使用新类型对象或重启；LRU 淘汰不能替代一致的类型更新机制。

## 实现调整

1. 验证器和路径声明查询统一通过 _SchemaKey：可哈希注解保留嵌套顺序语义，不可哈希 Annotated 通过对象身份缓存。
2. fields、_cached_adapter、parameter_types、_compiled_plan、_declared_path 各使用 lru_cache(maxsize=512)。限制的是根入口数，一个入口仍可引用多个子类型；不将 512 解释为总类型数或内存字节上限。
3. BaseTransport 每批绑定一次 plan.apply / plan.project，再处理每条消息或工具。未增加输入全量复制，未跳过 SDK 校验、序列化检查或覆盖钩子。

在实际五协议负载中，字段缓存使用 380 个入口，验证器 12 个、过滤根计划 33 个、路径声明 21 个，均在容量内；优化前后对应未命中数完全一致，观察到的负载没有因容量限制增加重新编译。

同一个 10 场景进程中，根计划查询总次数从 40,416 降到 5,808，减少约 85.63%。计划未命中仍为 33 次。这里减少的是缓存查找和缓存键构造，不是少处理了消息或缓存了请求结果。

## 独立协议批量微基准

协议字段使用 actor / utterance、action / schema，未使用任何内置协议的消息结构。每批 100 条数据，保留开放工具 Schema 的所有权复制。每次预热 10 次，再采样 9 个批次均值，每个均值来自 200 次调用；采用与原生确认相同的前、后、后、前进程顺序，合并每版本 18 个批次均值取中位数。

单位 µs / 100 条数据；该微基准不含真实 SDK 执行，不能将其百分比直接解释为完整请求收益。

| 操作 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 输入投影及 SDK 类型验证 | 152.79 | 131.89 | -13.68% |
| 消息过滤 | 42.37 | 23.27 | -45.09% |
| 工具过滤及 Schema 复制 | 100.12 | 84.93 | -15.18% |

## 原生完整请求确认

使用之前的默认复杂负载和真实官方 SDK，经 HTTPX 内存响应运行；保留 GC、序列化、完整流消费、响应关闭和最终结果副本。四个隔离进程按“前、后、后、前”运行，每进程每场景 20 个暖样本，合并后每版本每场景 40 样本，合计 800 个正式暖样本。计时排除 MyLLM 构造及验证断言；测量期间未启用 profiler。

十个原生场景的 P50 变化中位数为 **+0.08%**，范围 -2.52% 至 +2.94%。这组测量没有证明完整请求存在稳定的整体加速，也没有呈现明显的普遍回退。P95 依然受 GC / 调度长尾影响；没有在本轮对每个正式样本安装 GC 回调，不能逐一归因。
完整请求的工作量主要仍在 SDK、消息/工具内容处理和流累积；缓存已经命中时，消除部分查询的收益较小。因此保留这次改动的理由是通用性修复、有界增长和可测的批量效率，而非宣称端到端大幅提升。

## 正确性与可比性

- 全新的独立协议完成两次生成，使用不可哈希 Annotated 消息与请求字段，显式扩展路径得到正确结果，客户端复用且响应和客户端按各自生命周期关闭。
- 新增同名类型隔离、Union 验证器顺序、缓存淘汰重编译测试；100 消息和 100 工具批次只建立两个根查询键，工具 Schema 保持输入输出隔离。
- 所有正式进程的 Python、SDK、负载大小、分块、计时定义一致；请求字节、响应字节、事件数、消息数、工具数、并行调用数和输出事件数逐项相同。
- 原有递归类型、委派路径隔离、开放字典、显式 None、未知字段不读取、请求 payload 不被缓存持有的测试继续通过。

最终验证：全量 **1952 passed in 15.80s**；Ruff 检查、Python 格式检查、git diff --check 通过。
