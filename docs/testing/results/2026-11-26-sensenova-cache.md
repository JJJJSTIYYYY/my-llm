## 初次失败和补跑

初次矩阵为 11 个组合完成、一个组合未完成。Responses 上游／middleware 输入首轮未满足
正文精确等于 READY 的判据，首轮补跑再次失败，第三次尝试四轮全部通过。
原始报告的 `previous_attempts` 保存前两次失败，没有覆盖成成功或删除失败。
共执行 **50 次真实请求**：最终成功会话 48 次，另外两次首轮尝试。

失败均为调用层正文检查的 AssertionError，没有 SDK 网络或限额异常。为避免正文不匹配
阻断缓存测量，探针随后将 `answer_matches` 与 usage 采集分开：正文失败仍使组合失败，
但继续后续轮次；工具参数、前缀或网络错误仍终止。第三次尝试全部正文检查本身也通过，
没有通过放宽判据获得成功。前两次未保留正文，无法进一步判断它们具体回答了什么。

首个失败的 HTTP 状态原本被探针的断言错误处理覆盖为 null；已修正为保留观察状态，
该历史字段不补造。第二次尝试及最终所有成功请求均记录 HTTP 200。

## 追加对照：Chat→Chat 为什么只有 1/3

原矩阵这一格只有三个后续请求，缓存序列为 `[0, 0, 0, 5888]`。
前缀和工具声明均一致，不能据此将低命中归因于同协议转换。矩阵各格采用独立随机上下文，
按顺序调用，也不是协议间缓存效率的受控比较。

为核对请求 JSON 变化的影响，额外对一个新 Chat→Chat 会话重复六次完全相同的输入批次。
开启本地消息缓存，重复批次按重试处理，不追加上一轮输出；公开返回模式交替，
每次底层仍请求 SSE。各轮等待时间为 0、2、2、10、2、2 秒。
完整 HTTP 请求体解析为 JSON 后，以键排序、紧凑格式计算 SHA-256，六次均为
`00b214c857fd86c2a32212e083a591d4c8f57941747c4bf9f19ccd5621328811`。

| 次数 | 公开 stream | 总输入 token | 服务端 cached_tokens |
| --- | --- | --- | --- |
| 1 | False | 5858 | 0 |
| 2 | True | 5858 | 5632 |
| 3 | False | 5858 | 0 |
| 4 | True | 5858 | 5632 |
| 5 | False | 5858 | 0 |
| 6 | True | 5858 | 5632 |

六次均为 HTTP 200。这说明在请求 JSON 不变时也观察到服务端计数不同，排除了
“协议转换改变请求 JSON”作为本次对照差异的解释；不能据此确定缓存路由、预热、回收或
其他服务端内部条件中的哪一个是原因。公开 stream 模式与计数在本小样本中交替相关，
但两者的上游请求 JSON 相同，尚未验证其他传输因素，也不把相关性解释为因果。

追加对照原始数值保存在 `/tmp/sensenova-identical-cache-results.json`，临时驱动为
`/tmp/sensenova-identical-cache-probe.py`，均不包含密钥。本对照独立于原矩阵统计；
包含它后，本次累计真实请求为 56 次，仍未遇到限额异常。
