# Parameter / Config 重构性能复测

测试日期：2026-10-20（Asia/Shanghai）。对照用户提供的[重构前性能报告](performance-regression-2026-10-20.md)，重新运行其“修复后”源码与本轮 Parameter / Config 重构后的源码。

## 结论

**主要收益在实例构造，完整请求的 P50 大致持平、略有改善；尾延迟没有一致改善。**

- 预热后 MyLLM 构造从约 2.2–2.4 ms 降到 0.067–0.072 ms，五协议均减少约 97%，约快 32–34 倍。此项单独测量，原完整请求基准不包含构造。
- 完整 60 场景逐场景 P50 变化中位数为 **-1.96%**，45 个下降、15 个上升；53 个位于 ±5% 内。
- 交替进程确认的原生场景中，除 Gemini 流式外，其余九项 P50 变化在 -2.49% 至 +0.98% 之间，没有显示明显的核心路径回退。这个区间是本次观测，不是显著性结论。
- Gemini 流式的 -37.88% 不解释为稳定计算加速：其 P50 会随第二代 GC 是否覆盖约半数样本而跳动，独立 GC 诊断中的两版流式 P50 又回到接近水平。
- 四项原生场景的 P95 明显上升：Chat 收集、Responses 流式、Anthropic 收集、Ollama 流式。40 样本的 P95 对少量 GC / 调度长尾敏感；当前数据不支持“所有延迟指标都改善”的结论。

两个版本使用相同 Python、SDK、复杂负载、HTTP 分块、runner、内存传输和验证器。负载模块通过 AST 核对：仅 Profile 构造工厂及其 wrapper 导入不同，其余消息、工具、事件、控制参数的构造逻辑一致。API 适配只在隔离测试负载中完成，未给新运行时增加旧版兼容层。

## 方法与范围

- 正式完整矩阵：先重构后、再重构前；各 60 场景，每场景 10 个暖样本，独立预检、一次冷调用和额外两次预热。
- 原生确认：四个独立进程按“前、后、后、前”运行；每进程 10 场景、每场景 20 个暖样本，合并后每版本每场景 40 个样本。
- 正式延迟测量合计 2000 个暖样本，全部保留默认 GC；未在计时期间启用 profiler 或 GC 回调。
- 真实官方 SDK 使用 HTTPX 内存响应，不建立 socket、不等待网络或模型推理；计时包含请求准备、序列化、响应解析、完整消费、响应关闭和最终结果副本。
- MyLLM 构造、负载准备、验证断言及实例关闭不在完整请求计时内；cold 指预检后的新实例首次 generate，包含延迟创建 SDK 客户端，不代表全新 Python 进程或首次 Schema 编译。
- 构造诊断：每协议预热 10 次，再测 300 次固定 Provider/Model 的同步 MyLLM 构造，保留默认 GC，确认未创建 SDK 客户端；不代表动态类型首次解析成本。
- GC 诊断在另两个独立进程进行，每版本 10 个原生场景各 20 样本；回调开销及扣除暂停后的数值只用于归因，不混入正式延迟结果。

默认负载：12 轮历史、12 个工具、每轮 4 个并行调用，用户文本 2048 字符、输出 8192 字符、3 层 Schema、8 条嵌套参数记录、96 字符增量；HTTP 分块 1024 字节。

负载使用固定 Profile 类型和标准参数路径，显式传入 max_tokens；这些结果不覆盖所有自定义路径、动态类型或参数默认值组合。

## 预热后的实例构造

单位 µs，每协议每版本 300 样本；独立于下面的 generate 延迟。

| 协议 | 重构前 P50 | 重构后 P50 | 变化 | 加速比 |
| --- | ---: | ---: | ---: | ---: |
| Chat | 2234.13 | 66.71 | -97.01% | 33.5× |
| Responses | 2336.44 | 69.71 | -97.02% | 33.5× |
| Anthropic | 2326.06 | 71.75 | -96.92% | 32.4× |
| Gemini | 2365.73 | 68.79 | -97.09% | 34.4× |
| Ollama | 2236.02 | 68.54 | -96.93% | 32.6× |

调用计数诊断中，每次预热后的重构前构造仍调用 get_type_hints 11 次、_declarations 8 次；重构后这两项均命中有界声明缓存，不再进入对应函数体。路径解析也使用有界缓存；只对最终生效值捕获一次快照，冻结参数对象仅在可变默认值需要副本时替换。

这说明配置重构显著减少了重复类型分析，收益主要发生在构造阶段。对于长期复用 MyLLM 的应用，这通常是一次性收益；每次请求都新建实例的用法会更频繁地受益。此处没有用构造和请求各自的 P50 相加来声称端到端加速。

## GC 与尾延迟

首轮完整矩阵的 Gemini 原生收集 / 流式 P50 看起来分别上升 36.47% / 44.92%；但四进程确认又变为 -1.41% / -37.88%。同一源码在不同 GC 相位下能够落在约 47 ms 或约 76 ms 的不同中位数区间，不能据其中一组百分比判断计算路径退化或加速。

下面是另行启用 GC 回调的 Gemini 诊断，每场景每版本 20 样本，正式延迟表未扣除任何暂停。

| 模式 | 前观测 P50 | 后观测 P50 | 前 / 后 gen2 次数 | 前 / 后扣除记录 GC 后中位数 |
| --- | ---: | ---: | ---: | ---: |
| 收集 | 76.49 | 47.58 | 10 / 8 | 46.48 / 44.99 |
| 流式 | 47.98 | 48.27 | 7 / 8 | 45.55 / 45.45 |

本次诊断中的 Gemini 第二代 GC 平均暂停约 37–44 ms，足以改变 20 或 40 样本的 P50 / P95。原生其他协议也观察到约 30–57 ms 的第二代回收。该诊断支持“GC 是重要波动来源”，但没有逐一回溯正式样本中的长尾，所以不把所有 P95 上升都归因于 GC，也不据此排除调度或真实尾延迟回退。

对 P95 有硬要求时，需要更长样本及重复、交替的独立进程测量；这轮能确认的是构造成本大幅下降，典型完整请求没有出现普遍明显回退，尾延迟仍需单独关注。

## 执行路径的解释

- 主要结构性收益：有界类型声明缓存避免每个实例重复解析相同 Profile 注解；路径语法解析缓存避免逐块重复执行正则。
- 请求期改动较小：phase 隔离、基类统一组装、移除 encode 配置对 decoder 输出的反向路由，不改变真实 SDK、标准消息转换、流状态累积和结果所有权。
- 对单次暖流式调用的独立 cProfile 计数，五协议 deepcopy 总次数分别仅减少 3、3、3、3、3 次，不能把原报告中此前的大幅复制优化算成本轮配置重构的收益。
- cProfile 会放大耗时，函数累计耗时互相重叠。此处仅用于确认调用次数和热点，不作为真实延迟或互斥耗时占比。
