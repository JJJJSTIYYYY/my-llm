# 项目结构规划

## 定位与范围

提供统一的 Python LLM 调用入口，将不同供应商的请求、响应、流式事件和
异常转换成稳定的公共接口。首版建议聚焦聊天生成、同步与异步调用、流式
响应以及工具调用；多模态、结构化输出和 embeddings 按实际需求逐步扩展。

此处的接口与模块名属于规划，不代表已经实现或承诺支持这些能力。
发布名称暂用现有的 `my-llm`，导入包名为 `my_llm`。

## 当前目录骨架

采用 `src` 布局，将可分发的库与仓库中的测试、文档和示例分开。
这种布局有助于发现本地源码可导入、安装后的包却缺少文件的问题。
依据：[PyPA 的 src 布局说明](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)。

```text
my-llm/
├── pyproject.toml                # 包元数据，后续补充构建、依赖与工具配置
├── README.md                     # 项目介绍，未来兼作 PyPI 项目说明
├── .gitignore
├── .python-version              # 本地开发解释器版本
├── .github/
│   └── workflows/               # 未来放置 CI 与发布工作流
├── src/
│   └── my_llm/                  # 可安装的库；未来从这里导出公共接口
│       ├── types/               # 统一消息、请求、响应、工具和流式事件类型
│       ├── providers/           # 供应商协议适配
│       │   ├── openai/          # OpenAI 适配，端点实现按实际需求选择
│       │   ├── anthropic/       # Anthropic 适配
│       │   └── openai_compatible/ # 使用 OpenAI 兼容协议的服务适配
│       └── _internal/           # 内部共享机制，不承诺公共 API 稳定性
├── tests/
│   ├── unit/                    # 类型校验、转换、异常和内部逻辑
│   ├── contract/                # 各适配器遵守同一接口语义的测试
│   ├── integration/             # 需要真实服务与凭证的可选测试
│   ├── packaging/               # 构建产物、安装、导入和可选依赖检查
│   └── fixtures/                # 脱敏的请求、响应和流式事件样本
├── docs/
│   ├── project-structure.md     # 本文
│   ├── guides/                  # 使用方式与供应商接入指南
│   ├── providers/               # 供应商能力和差异说明
│   └── reference/               # 公共 API 参考
└── examples/                    # 将来放置基础、异步、流式和工具调用示例
```

空目录使用 `.gitkeep` 占位；该文件没有 Python 包语义，后续添加实际文件时移除。
当前不创建 `__init__.py`、其他 Python 文件或工作流配置。目录骨架本身尚不能
作为完整的库构建发布。

## 后续模块划分

先用少量文件承载职责，只有模块明显变大时再拆成子包。以下文件仅列入规划，
现阶段不创建。

| 未来位置（相对 `src/my_llm/`） | 职责 |
| --- | --- |
| `__init__.py` | 集中导出客户端、常用类型与异常，保持公开入口简洁 |
| `client.py` | 同步与异步客户端，协调配置、适配器选择及调用生命周期 |
| `config.py` | 凭证、基础地址、超时和重试配置；不保存全局共享客户端 |
| `exceptions.py` | 统一认证、限流、超时、服务端及不支持能力等异常 |
| `protocols.py` | 供应商适配器的同步、异步与流式接口约定 |
| `types/messages.py` | 消息、角色和内容块；为多模态内容保留扩展空间 |
| `types/requests.py` | 标准请求参数与受控的供应商专属选项 |
| `types/responses.py` | 统一输出、用量、结束原因与供应商元信息 |
| `types/streaming.py` | 文本增量、工具调用增量、用量和结束等事件 |
| `types/tools.py` | 工具描述、工具调用与工具结果的数据结构 |
| `providers/<provider>/adapter.py` | 实现该供应商的调用与流式处理 |
| `providers/<provider>/mapping.py` | 转换请求、响应和异常；随复杂度决定是否单独拆分 |
| `_internal/registry.py` | 适配器注册与查找，支持显式注入自定义适配器 |
| `_internal/retry.py` | 共享重试策略，避免与供应商 SDK 重复重试 |
| `py.typed` | 未来随构建产物分发的类型标记 |

如果采用供应商官方 SDK，连接与传输由 SDK 管理；只有确定使用直接 HTTP 调用时，
才在 `_internal/` 增加共享传输模块。

## 依赖方向与接口边界

- `types` 与 `exceptions` 保持基础性，不导入供应商 SDK 或客户端。
- `protocols` 依赖统一类型，描述适配器需要实现的行为。
- `providers` 依赖统一类型、接口约定和内部辅助模块；适配器之间不互相依赖。
- `client` 负责协调适配器；供应商请求转换集中在适配器内。
- `_internal` 只放多处需要的共享机制，不用于堆放尚未明确职责的代码。

统一接口需要保留供应商之间真实存在的差异：明确声明支持的能力，对不支持的
能力返回明确异常；供应商专属参数与标准参数分开，避免静默丢弃参数。
OpenAI 兼容服务共享协议适配器，但具体能力按服务声明，不能默认与 OpenAI 完全相同。

同步和异步客户端共享类型与转换规则。异步路径使用原生异步 I/O，后续设计要明确
连接关闭、取消和流式消费提前结束时的资源释放。流式事件保留工具调用标识与增量，
避免将所有事件压缩为文本字符串。重试要区分发送前失败与已经开始输出的情况，
避免用户收到重复内容。

## 测试与文档职责

`unit` 使用模拟请求和固定数据，覆盖参数校验、转换及错误处理。
`contract` 让所有适配器执行同一组行为检查，重点验证同步与异步结果一致性、
流式结束、工具调用、能力声明和资源释放。

`integration` 只在显式启用并提供凭证时访问真实服务。`fixtures` 保存脱敏样本，
测试和文档都不依赖真实密钥。`packaging` 在隔离环境安装 wheel，并检查导入、
类型标记及只安装某个供应商 extra 时的行为。

`docs/guides` 解释如何使用和扩展；`docs/providers` 记录支持能力与已知差异；
`docs/reference` 描述稳定的公开 API。`examples` 仅使用公开接口，避免依赖内部模块。

## PyPI 发布准备

现有 `pyproject.toml` 只有初始化元数据。后续实现开始时再配置以下事项：

1. 确认最终发布名及 PyPI 名称可用性；目前的名称只是暂定。
2. 声明构建后端和 `src/my_llm` 包发现规则；wheel 包含运行所需文件与类型标记，
   排除 `.gitkeep` 等占位文件，源码包按需包含测试和文档。
3. 完善描述、项目链接、支持的 Python 版本与许可证；选择许可证后添加根目录
   `LICENSE`，正式发布前添加 `CHANGELOG.md`。
4. 将必要的共享依赖放入核心依赖；采用供应商 SDK 时，可通过 `openai`、
   `anthropic` 等 extras 安装。缺少某个可选 SDK 不应阻止导入整个库。
5. 将测试、类型检查、格式检查和文档工具作为开发依赖管理，避免混入核心依赖。
6. 在 `workflows` 中加入质量检查与发布流程，构建 wheel 和源码包，验证安装后
   再发布。首次发布先通过 TestPyPI 验证。

构建系统、项目元数据和可选依赖的配置参考
[PyPA 的 pyproject.toml 指南](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/)。
本阶段保留现有 `pyproject.toml` 与 Python 版本设置，不提前选定构建后端或依赖。

## 推荐落地顺序

先确定公共类型、客户端接口与适配器约定，再实现一个供应商的完整调用链。
加入第二个供应商时，用契约测试验证统一接口是否成立，然后完善可选依赖、
安装产物验证与发布流程。后续有具体需求时再增加路由、缓存、框架集成等模块。
