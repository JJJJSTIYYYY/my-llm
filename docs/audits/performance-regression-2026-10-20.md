# 删除未知字段保留后的性能回退定位

本轮使用删除前提交 `b4120a221ae48e64098a53455cffb19446477c28`、删除提交
`d1cedebe9b2267d92d7cd880a022b59a1a46299f` 和当前工作区进行对照。
[此前复测](performance-retest-2026-10-20.md) 的 before / after 都已经删除该功能，
只能衡量后续清理的收益，不能回答删除本身是否引入回退。

## 已确认的额外工作

删除保留记录也移除了同协议 Decoder 的原始快照回放；现在同协议请求仍须逐字段翻译。
后续为保证“不读取未知字段”和公开结果隔离，又引入完整声明遍历、SDK 字段视图及流事件出口复制。
因此删除功能并不自动保证实际遍历次数减少。需要优化这些新增实现，不能恢复未知字段快照。

| 原因 | 本轮修复 | 诊断证据 |
| --- | --- | --- |
| 每个内容块给大量不匹配 Union 候选评分；每个字段再走通用字典/模型分派 | 编译 Literal 候选索引，提前排除不匹配候选；字典直接读取声明字段，保留原评分和并列顺序 | 默认复杂负载的输入投影与请求过滤：Responses 评分 9,198 → 794 次；Anthropic 5,560 → 442 次 |
| SDK 同一字段重复查找、包装嵌套列表和模型 | 单次转换的视图缓存字段、缺失结果与包装值；存在性检查不构造子视图 | 32 个子模型的列表读取三次：列表重建 3 → 1 次，子视图 96 → 32 个 |
| Gemini config.tools 随根配置过滤后又由工具入口过滤 | 根计划只借入声明的消息/工具叶，后续原有钩子过滤一次；其他配置照常隔离 | 回归测试验证工具 Schema 与旁路输出 Schema 各捕获一次，覆盖钩子仍执行 |
| 每个流事件在 Encoder / Decoder 出口深拷贝刚构造的完整容器 | `_chunks` 直接构造独立输出，只在实际借入可变字段时捕获；消息、工具及最终结果仍保持隔离 | Chat Decoder 单函数剖析中，成品复制占 instrumented 耗时约 81%，复制 288 个字典和 98 个列表 |

消息和工具的公开出口仍捕获整个已投影结果。这里的普通 dict / list 使用专门的 JSON 复制，
不可变叶直接复用，避免 Python 3.12 通用 deepcopy 对每个标量的 memo 查找和动态分派。
自定义容器、SDK 对象等继续调用标准 deepcopy，共享同一个 memo；别名、递归引用及自定义复制行为保持。
这项优化只应用在翻译后的结果，不会遍历原始协议中的未知字段。

视图的数据缓存只属于当前转换，随转换释放；全局 Schema 计划缓存只保存类型规则和不可变路径。
没有恢复全 SDK `model_dump()`、未知字段读取、原始消息回放或跨请求数据缓存。
所有协议继续经过 Encoder、Decoder、Transport 和同一个流状态机。

同时修复 Anthropic 标准工具字段 `cache_control` 丢失，保留 `type`、`ttl` 及显式 `None`。
性能比较不以删除这类标准字段来减少负载。

## 验证方法

同机、相同 Python 与 SDK、相同复杂负载；真实官方 SDK 经 HTTPX 内存响应工作，包含序列化、解析、
完整流消费、响应关闭和最终结果副本，不等待网络或模型推理。
默认 60 场景覆盖五种原生协议与五乘五跨协议组合，各含收集及完整流式模式。
默认 GC 开启；每个场景独立预检、冷调用、额外预热两次，再测十次。
计时及字段核对规则见[性能测试指南](../guides/performance.md)。

与删除前相比，Chat 九条文本列表归一化成字符串，Responses 两条系统消息显式构造成 input_text 列表；
文本和工具参数相同。Gemini、Ollama 的原生 SDK 请求逐值相同；修复后 Anthropic 也恢复相同标准字段。
这些序列化表示差异需记录，不能声称历史请求字节完全一致。

## 交替对照结果

三个版本各在两个独立进程运行原生场景，顺序为修复前、修复后、删除前，再反向运行。
每个进程每场景测 20 个暖样本，以下 P50 合并每个版本、每个场景的 40 个样本，单位 ms。
该顺序平衡先后位置，没有进行统计显著性检验；接近零的差异视为持平。

| Chat | 完整流式 | 24.03 | 27.03 | 23.91 | -11.53% |

| Responses | 完整流式 | 65.09 | 65.89 | 61.47 | -6.70% |

修复后相对本轮修复前，58 个场景 P50 下降，逐场景变化中位数 **-10.19%**；

## 遍历与 GC 的归因验证

对相同复杂原生事件，单独剖析 Encoder.chunks 与 Decoder.chunks。
下表的 deepcopy 次数包含递归调用，并非整个请求的副本数；这项诊断不计消息、工具出口的 JSON capture。
所有十组输出的 JSON 摘要在修复前后完全相同。

| 协议 | Encoder deepcopy 调用：前 → 后 | Decoder deepcopy 调用：前 → 后 |
| --- | ---: | ---: |
| Chat | 6343 → 898 | 2102 → 86 |
| Responses | 11712 → 3534 | 2133 → 366 |
| Anthropic | 5226 → 290 | 1432 → 108 |
| Gemini | 4041 → 1504 | 3693 → 1064 |
| Ollama | 4403 → 1394 | 2282 → 1064 |

例如 Chat Decoder 不再复制 288 个新建字典和 98 个新建列表，剩余 86 次是对增量值的字段捕获；
合法字符串直接复用。开放对象仍建立独立副本，未用少处理内容换取耗时下降。

Gemini 的 P50 对 GC 阶段敏感。本轮完整矩阵的 Gemini 流式中位数曾高于修复前，
所以不能仅看这一组十样本的百分比判断回退。
另用相同负载做 20 次 GC 回调归因，保持默认阈值、真实 SDK 与完整验证：
其中十次 generation 2 回收合计约 322 ms；77–84 ms 的高峰包含约 33–38 ms 的 GC 暂停。
总耗时减去已记录 GC 暂停后的中位数约 45.39 ms，仅作为归因参考。
正式性能结果始终包含默认 GC；没有关闭 GC，也没有从正式样本里扣除暂停。

cProfile 会放大耗时，累计时间相互重叠；GC 回调也属于诊断工具。
延迟结论使用上面的无 profiler、无 GC 回调基准，诊断仅用于确认重复工作和解释波动。

## 验证与复现

- 全量测试：**1899 passed in 17.08s**，覆盖标准字段、未知字段不读取、公开转换双向隔离、请求间隔离、流状态缓存、响应关闭及全部性能路径。
- Ruff 检查、Python 源码格式检查、git diff --check 通过。
- 新增流隔离矩阵覆盖五种 Encoder、五乘五 Decoder、开放参数 / 元数据 / logprobs 字节列表，以及独立第六协议。
- JSON capture 覆盖自定义复制、共享引用、递归引用与 SDK 对象的既有所有权测试。
- 过滤计划覆盖重叠 / 缺失判别值、同分顺序、递归类型、显式 None、未知字段禁止扫描和不同委派路径的缓存隔离。

