## 保留差异：CI 的旧接口断言

[ci.yml](../../.github/workflows/ci.yml) 的隔离 wheel 导入步骤仍检查：

```python
assert callable(my_llm.generate)
assert not MyCodec().codecs
```

前者出现在安装全部 SDK 后，后者出现在仅安装核心包时；全部 SDK 的分支还读取 `MyCodec().codecs`。
但[包导出](../../src/my_llm/__init__.py)已经删除顶层 `generate`，
公开入口为 `MyLLM.generate`；[发行包测试](../../tests/packaging/test_distribution.py)也验证不存在旧名称。
[MyCodec](../../src/my_llm/codec/converter.py) 的组件映射现为私有 `_codecs`，不提供公开 `codecs` 属性。
因此这些断言与源码契约矛盾。即使常规测试通过，也不能据此声称当前 CI 整体通过。
本轮禁止修改代码与测试，工作流保持原样，文档没有承诺其执行成功。

手工验证应按[发行包验证](../testing/packaging.md)检查 `MyLLM.generate`、`MyCodec` 翻译行为及包版本。
该差异只影响验证步骤，不改变库的公开调用方式；后续若调整 CI，应直接将断言对齐公开契约，
无需恢复旧导出或新增兼容包装。

## 后续 CI 修复

2026-11-23 收到 CI 失败后，修复范围扩展到示例和工作流。此前“未改 CI”描述的是文档整理阶段。
根因是收窄公开业务接口时，未同步所有消费者：`examples/local_demo.py` 仍遍历 `codec.codecs`，
CI 的隔离安装步骤也读取该属性及顶层 `my_llm.generate`。常规 pytest 未执行这个本地示例及完整 CI shell 步骤，
因此测试通过没有暴露这些遗留引用。

示例现在显式演示三种内置协议并调用公开 `convert`。CI 的核心安装检查通过公开 `encode` 验证缺失 SDK 的错误，
安装全部 SDK 后检查 `MyLLM.generate` 和三协议 `encode` 行为。没有恢复旧导出，也没有改为访问 `_codecs`。

本地示例、2767 项既有测试及 Ruff 检查通过；发行包隔离验证使用从工作流提取的 shell 步骤，
只将 wheel 路径和临时目录改为本机位置。远程 CI 的最终状态需由推送后的运行确认。
